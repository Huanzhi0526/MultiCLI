# Sol / DeepSeek 验收和提交规范

## 1. 权责

| 工作 | Sol | DeepSeek |
|---|---|---|
| 环境安装、参考下载、上游基线、GitHub 远端 | 执行与记录 | 提供需求，不擅改 |
| 架构、接口、范围、任务拆分 | 决定并冻结 | 遵守；提出问题与建议 |
| 产品代码、实现所需测试、技术说明 | 原则上不代写大块功能 | 实现并自测 |
| 独立验收、反例、真实 Windows 操作 | 执行并决定结果 | 提供复现协助，按缺陷返工 |
| commit、push、tag、PR/合并、发布物上传 | 唯一操作者 | 禁止 |
| 项目状态和下一阶段派发 | 唯一维护者 | 只写回交状态 |

仅两个执行角色，不自行扩增第三名开发/验收 Agent。此方案本身不启动任何委派，也不启用 CodeBuddy 项目循环。后续用 DSH、CodeBuddy 或其他宿主承载 DeepSeek，由实际用户启用的工具流程决定；不能因为方案里写 DeepSeek 就擅自替换模型或启动 Baton。

## 2. 单批次状态机

`NOT_RUN → READY → IN_PROGRESS → SUBMITTED → ACCEPTED → COMMITTED → PUSHED`

验收失败为 `REWORK_REQUIRED`，修复后重新 SUBMITTED。外部条件缺失用 `BLOCKED`，同时写清已完成部分；不能拿 BLOCKED 当成功。`ACCEPTED` 仅代表明确覆盖范围，未跑项仍为 NOT_RUN。提交、推送和 CI 都是独立字段；exit code=0 或开发模型说“完成”不代表验收通过。

下一批要求当前批 ACCEPTED、已提交且工作区状态可解释。网络阻断时允许继续下一个已授权本地批次，但记录 `PUSH_PENDING`；最终交付必须补推送，不能把 GitHub 失败藏在“已完成”中。

## 3. 派工与回交

1. Sol 确认基线 HEAD、分支、未提交文件与前一验收状态。保留用户原有改动；不能清理不认识的文件。
2. 任务卡写明 id、目标、base_commit、允许改动路径、禁止范围、前置接口、验收案例、真实环境要求。一次只发一个子任务。
3. DeepSeek 修改授权文件并运行相关测试。只能读取 git status/diff/log；不操作暂存区、分支、commit、reset、checkout、stash、clean、远端或 GitHub 写入。
4. DeepSeek 回交实际改动列表、测试命令/结果、未测项、证据位置、已知问题，不给自己写 ACCEPTED。
5. 回交后进入冻结，DeepSeek 停止写文件。Sol 检查 base HEAD 未变、目录范围和新增文件，然后独立验收。
6. Sol 发现问题开 `Sxx-Rn` 缺陷单，写复现步骤、预期/实际、严重度、必要修复范围；返工不可改验收标准来通过。

共享一个 checkout，串行写入最简单。无需为了两角色强行建立多个 worktree；真需要隔离时由 Sol 管理。

## 4. 三层验证必须分开

**开发自测**：DeepSeek 测自己实现，允许使用 fixture、mock、单元和集成测试。

**独立验收**：Sol 阅读 diff，独立选择输入和反例；操作真实 Windows 应用、观察实际源文件/进程/数据，不只重跑开发者脚本。Sol 也不能把自己 S00 的 smoke 当最终产品验收。

**发布验收**：从 Sol 已提交的源码构建用户级安装包，干净配置环境安装、升级、退出、重开和卸载验证；记录二进制 SHA256 与源码 commit。使用真实账户测试不在 CI 保存凭据。

## 6. 性能目标与测量

S00 记录 OS、CPU、内存、存储和工具版本，测试排除模型网络响应时间。以下是首版验收目标，不是已测数据：

- 正常桌面进程数量下外部发现 p95 ≤ 10 秒；进程扫描默认 3 秒一次，后台可降频。
- 合成 10,000 会话 / 100,000 条消息、暖缓存：列表与限制返回条数的搜索 p95 ≤ 1 秒；索引后台进行，界面可交互。
- 无 CLI 负载、无导入时，应用及自有辅助进程空闲 5 分钟平均 CPU ≤ 整机 2%，工作集目标 ≤ 500 MiB；OS/WebView2 统计口径在报告中注明。
- 8 个托管终端同时输出，每个 100 KiB/s 持续 60 秒：当前终端输入回显 p95 ≤ 200 ms，无跨终端串流、无 UI 长时间冻结；超限按明确背压/日志策略处理。
- 每终端内存缓冲初始上限 4 MiB、日志初始上限 20 MiB，保留量可配置；同负载循环 20 次后不存在持续增长的活跃句柄或孤儿子进程。

若目标不适合实际机器，由 Sol 在实现前记录理由与新值，保留原值，不能在失败后无说明放宽。标准输出 flood 测试用本地辅助程序，不消耗模型额度。

## 7. Git 和 GitHub

正式仓库置于 app；参考仓库、scratch、原始日志、数据库、.env、凭据、真实会话和安装产物排除。仓库内保留合成 fixture、简洁验收摘要、许可证、lockfile 和能力表。自动检查不能替代人工审阅新增文件。

首选派生方式：Sol 用上游已通过 S00 的固定 commit 建立本地派生分支，用户远端作为 origin，上游作为 upstream；保留上游历史。GitHub 是否显示 fork 网络与技术派生无关，不默认公开。如果目标远端已有内容，先检查差异和历史，不 force push，不用 unrelated-histories 强行合并。

DeepSeek 提交前不存在自己的 commit。Sol 验收通过后：

1. 保存受测源码文件清单与 SHA256、base_commit、未跟踪源码列表；报告排除自身，避免哈希循环。可用 `git diff --binary` 加独立 untracked manifest 留证。
2. 检查许可证、密钥、用户数据与越界修改。验收期间源码变动则相关验证失效。
3. 只暂存明确通过的文件；不要盲目 `git add .`。Sol 提交，建议消息 `feat(discovery): ... [S02-02]`。
4. 核对提交中的源码与受测文件摘要一致；只有文档回填可不重跑产品测试，源码变化必须补验证。
5. Sol 推送用户指定分支，核实远端 commit。CI 通过状态单独记；只有 build 通过不覆盖真实桌面测试。
6. `main` 只接纳通过验收批次；可用阶段分支加 PR，由 Sol 创建与合并。保护分支要求人工或额外 reviewer 时按真实规则执行，不绕过。

GitHub Actions 首版做 Windows 依赖恢复、类型/格式、Rust 与前端相关测试、fixture/协议检查、安装包构建。不在 Actions 登录用户 CLI 账号。签名证书未提供时交付“未签名测试安装包”，不宣传已签名；提交 GitHub 不自动等于发布公开 Release，公开发布需用户对应范围授权。

## 8. 完成标准

S00–S07 都有独立结果；R01–R09 对应覆盖完整；P0 真实链路通过；P1 明确实测覆盖与未测项；已知缺陷无阻断；安装包及源码可追溯；用户远端已同步；文档能指导使用与卸载。

可选 psmux、远程、其他候选 CLI 可保持 NOT_RUN，不影响首版。但三核心历史/交互、全局发现、双向查看等硬范围未过时只能交 Alpha/阶段成果，不能宣布首版完成。
