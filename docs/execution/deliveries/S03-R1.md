### R1-01 按预算续读与完成状态（P1）

- **现象**：12 条消息、`max_bytes_per_file=400`，首 pass 只导入 2 条却报
  `complete=true`，之后 11 个 pass 仍是 2 条；普通 JSONL 与 `.zst` 都复现。默认预算下
  约 38 MB / 160 条只导入 140 条仍报 `complete=true`。
- **根因**：游标只记录 `committedOffset`，没有“是否读到 EOF”；`decide` 在
  `size`+`mtime` 相同时直接 `Skip`，于是“预算停在中间”的文件永远被当成未变化。
  `ScanReport.complete` 只看目录遍历，不看单文件是否读完。压缩流的逻辑偏移被当成文件
  物理偏移处理，续读会从错误位置开始。
- **方案**：
  - 游标新增 `read_complete`（只有真正读到 EOF 或“半行等待”才为 1）与
    `lines_committed`；`decide` 先判 `read_complete=false → Append`，再做 size/mtime 判断。
  - `ScanReport.complete` 现在要求：整棵树列完、没有停下、没有未读文件、没有失败文件、
    没有行错误。任何一项不满足就是 `false`，且引擎把“只是没读完”记为 `partial` 而不是 `ok`。
  - 压缩流：`committedOffset` 明确是**解压后**的逻辑偏移，`size_bytes` 仍是物理大小；
    续读时从头解码并丢弃已提交前缀（受 4 s pass 预算、1.5 s 文件预算、256 MiB 解压上限与
    取消检查约束），不再“每次只重读第一段”。
  - 每个文件一个独立事务，并有自己的 1.5 s 预算；超大文件被切成多个 pass 提交，单一
    SQLite 连接不会被一个 38 MB 文件长期占用。
- **证据**：`tests::a_byte_budget_stop_is_reported_incomplete_and_the_next_pass_finishes`、
  `tests::a_compressed_budget_stop_resumes_from_the_logical_checkpoint`、
  `tests::a_completed_file_reports_complete_and_stops_re_reading`；主管 probe
  `sol_plain_file_resumes_after_per_file_budget`、`sol_zstd_file_resumes_after_per_file_budget`、
  `sol_default_budget_reports_unread_file_content`。

### R1-02 恢复 parser 状态与稳定身份（P1）

- **现象**：无 event id 的 Codex 消息跨 3 次追加后 4 条只剩 2 条；带合法 header 的文件改名
  为 `renamed.jsonl` 后追加一条，会话从 1 个变成 2 个。
- **根因**：`line_index` 每个 pass 从 0 开始，fallback `source_key`（`kind:line`）与旧行冲突；
  追加时不会重读文件头，parser 的 `native_id` 为空，退回按文件名猜会话。
- **方案**：游标持久化 `parser_state_json`（native session id、cwd、`runtime_workspace_roots`、
  待应用标题及其来源、是否已取过标题），三个 parser 都实现 `checkpoint()` / `restore()`；
  行号从 `lines_committed` 继续。一次性全读与增量读取产生相同的 `sourceKey`。
  没有检查点（或检查点无法解析）的游标一律整读一次，不猜行号。
- **证据**：`tests::an_append_without_native_event_ids_keeps_one_message_per_line`、
  `tests::a_renamed_transcript_keeps_its_header_session_on_append`、
  `tests::a_restart_between_appends_keeps_identity_and_line_numbers`；probe
  `sol_append_without_native_event_id_never_drops_new_messages`、
  `sol_renamed_transcript_append_keeps_header_session_identity`。

### R1-03 完整的多文件贡献关系（P1）

- **现象**：同一来源两个文件提供相同两条消息；按路径排序后第二个是副本，把副本截断为 0
  再扫描，消息从 2 变 0，原文件仍完好。
- **根因**：`history_message_origins` 主键是 `(message_id, source_id)`，upsert 覆盖前一个
  文件的 `file_identity`；清理时又只检查“其它 source”，不检查同 source 的其它文件。
- **方案**：主键改为 `(message_id, source_id, file_identity)`；清理算法改成
  ①收集该文件贡献过的消息 id ②删除该文件的 origins ③只删除**再无任何 origins** 的消息
  （FTS 行与 messages 同批删除）。会话 id、备注与标签不受影响。
- **证据**：`tests::two_files_of_one_source_both_keep_provenance`、
  `tests::a_rebuild_removes_only_unreferenced_messages`；probe
  `sol_multiple_files_keep_all_provenance_for_one_message`；v5 迁移测试
  `tests::schema_v5_migrates_a_populated_v4_database` 证明旧库升级后仍能插入第二条贡献。

### R1-04 递归来源边界（P1）

- **现象**：被允许的根内 `.ssh` 子目录中的合成 JSONL 被导入。
- **根因**：受保护目录规则只在 `validate_source_root` 对根路径本身生效，递归遍历没有复用。
- **方案**：新增 `history/guard.rs`，把规则变成“路径组件”的函数：任意深度、大小写不敏感、
  去掉 Windows 会忽略的尾随点/空格，另含 `Microsoft\Credentials` 这类二元组；遍历时对每个
  目录/文件先按名字判，再对 canonical 化后的相对组件判一次（覆盖 8.3 别名）。
  `contained_canonical` 保证 canonical 结果仍位于根内；仍然不跟随 symlink/junction。
  正常产品历史子目录（如 `sessions/2026/11/02`）不受影响。
- **证据**：`tests::a_nested_protected_directory_is_never_walked`、
  `#[cfg(windows)] tests::a_junction_below_the_root_is_not_followed`、`guard` 单元测试；
  probe `sol_nested_credentials_are_not_scanned`。

### R1-05 替换/改写的完整性复核（P1）

- **现象**：首尾各超过 4 KiB，中间 `OLD→NEW` 等长替换并恢复 mtime，索引一直保持旧正文。
- **根因**：只有「前 4 KiB 前缀 hash + 已提交末尾 4 KiB 锚点 hash」，中间的字节从未被比较。
- **方案**：每个文件按 256 KiB 分块保存 SHA-256（`history_file_blocks`）。每 pass 对每个
  文件复核一个窗口（`verifyOffset` 前进），全局 8 MiB/pass；走完整个文件回到 0。
  不一致 → 整文件重读。追加前额外比对“偏移所在的那个半块”，避免 append 把刚被改写的
  尾部当成新内容吸收。等长但 mtime 变化也走复核而不是 append。
  压缩文件按解压后的逻辑长度整段复核（同一遍解码即可比对，单文件上限 64 MiB，超出走物理
  size/mtime 与前缀 hash）。
- **检测上界**：单文件一个完整周期 = `ceil(已提交字节 / 1 MiB)` 个复核窗口；每个 pass 全局
  只有 8 MiB 预算，所以总量 B 的语料至少需要 `ceil(B / 8 MiB)` 个 pass 才能覆盖一轮。
  已完成一轮的文件在 15 分钟冷却期内不重复复核，把预算让给尚未复核的文件（否则预算永远
  花在路径最前面的那批文件上）。周期内每个**已提交**字节都会被比较一次，**不存在永远看不到
  的中间改写**；改写发生在该块被复核之前还是之后，决定它在本周期还是下一周期被发现
  （最坏约两个周期）。已知代价写在“限制”里。
- **证据**：`tests::a_same_size_middle_rewrite_is_found_by_the_verification_cycle`、
  `tests::an_append_cannot_hide_a_rewrite_just_before_the_offset`、
  `tests::a_same_size_rewrite_with_a_new_mtime_is_verified`、
  `tests::an_unchanged_file_is_verified_without_reimporting`、
  `tests::an_atomic_replacement_swaps_the_transcript`、
  `tests::a_compressed_transcript_replacement_is_detected`、
  `tests::an_mtime_rollback_with_growth_is_still_an_append`；probe
  `sol_middle_rewrite_with_same_size_and_mtime_is_seen`。

### R1-06 坏行与错误状态（P1）

- **现象**：首行坏 JSON、后面是合法 header+2 消息 → 整文件拒绝、0 条；合法 header 后坏行
  再接合法消息 → 状态仍 `ok`、`error=null`、`complete=true`。
- **根因**：首行解析失败即判 `unsupported`；行错误只累加到游标的私有计数，从不进入
  `ScanReport`/状态。
- **方案**：格式探测改为“最多 64 行或到 EOF，期间没有任何可识别记录才判选错产品”；坏行
  隔离为 `invalid-json` 并继续。行错误、`ingest-rejected`、`oversized` 进入
  `ScanReport.issues`（带 `fileIndex`/`line`/原因，**不带正文**），来源状态变
  `partial` 且 `error.details.issues` 列出前 8 条；`complete` 随之为 false。
  选错产品/完全无合法格式仍被拒绝（不是“取消格式检查”）。单行超过 1 MiB + 16 MiB 跳过
  上限时整文件 `unsupported`，不会无限读巨型行。
- **证据**：`tests::a_bad_first_line_does_not_reject_the_transcript`、
  `tests::a_wrong_product_file_is_still_rejected`、
  `tests::line_and_oversized_diagnostics_reach_the_source_status`、
  `tests::an_oversized_record_is_isolated_and_reported`；probe
  `sol_bad_first_line_does_not_hide_following_valid_transcript`、
  `sol_bad_rows_surface_in_index_status`。

### R1-07 查询/会话/版本绑定的分页（P2）

- **现象**：关键字 A 的游标用于关键字 B 仍被接受；Session A 的消息游标用于 Session B 也被接受。
- **根因**：游标只携带排序键与 `sort` 标签，没有查询/会话/数据代次指纹。
- **方案**：消息游标绑定 `sessionId` 与派生数据代次 `epoch`；搜索游标绑定规范化关键字的
  指纹、`workspaceId/agentId/sourceId` 指纹、匹配模式与 `epoch`。`epoch` 是
  `history_meta.purgeEpoch`，只在真正删除派生行（重建/截断）时自增，普通增量导入不会让
  翻页失效。错用一律 `invalid_argument`（`field:"cursor"`），不会成功空页或静默漏项。
  前端在关键字/过滤变化时丢弃游标，`ResumeBlock` 与新的会话详情都加了迟到响应保护。
- **证据**：`tests::a_search_cursor_is_rejected_after_a_rebuild`、
  `tests::a_message_cursor_is_rejected_for_another_session`、
  `tests::paginating_one_query_is_stable_and_does_not_repeat_rows`、model 单测
  `a_search_cursor_is_bound_to_its_query_filters_mode_and_epoch`；probe
  `sol_cursor_cannot_cross_search_filters`、`sol_message_cursor_cannot_cross_sessions`；
  前端 `drops a late detail page from a previously selected session`。

### R1-08 所有历史入口的有界详情（P1）

- **现象**：`SessionBrowser.tsx:56` 仍调用 `api.getSession` 全量取 `messages`；工作区/Agent
  入口能打开历史会话，历史页的分页没有覆盖它们。
- **根因**：S01 的详情是一个“整会话”DTO，历史页另行实现了分页，两条链路没有统一。
- **方案**：新增 `useSessionDetail`（`src/multicli/usePagedResource.ts`），用
  `multicli_get_session_metadata` + `multicli_list_session_messages`（每页 100）构建详情；
  `SessionBrowser` 改用它，工作区、Agent 与搜索三个入口因此是同一套有界链路。
  详情显示「历史会话 · 分页」徽标与「已加载 x/y」，有下一页时给「加载更多消息」，失败就地
  重试并保留已加载行。`multicli_get_session` 原样保留（兼容），只是 UI 不再调用。
- **证据**：前端 `reads a session through metadata plus one bounded message page`、
  `drops a late detail page from a previously selected session`；S01 的
  `opens the same session from workspace and agent entries with identical counts` 保持通过。

### R1-09 性能与公开资料（验收补项）

- **现象**：带 `agentId/workspaceId/sourceId` 的宽泛搜索约 1.3 s，未满足原卡 p95 ≤ 1 s。
- **根因**：过滤走 `history_message_fts JOIN messages JOIN sessions`，10 万命中要回表两次
  （计数一次、取页一次）。无过滤路径已经只查 FTS，过滤路径没有享受同样的优化。
- **方案**：把过滤条件下推到 FTS 行：`agent_id` 用
  `session_id IN (SELECT id FROM sessions WHERE agent_id=?)`，工作区用
  `session_id IN (SELECT session_id FROM session_workspaces WHERE workspace_id=?)`，
  来源用 `EXISTS(... origins WHERE message_id=? AND source_id=?)`；计数与取页都只扫 FTS，
  最后按主键回填 50 行。为此在 v5 增加 `ix_session_workspaces_workspace` 与
  `ix_history_origins_source_message`。回填缺失（FTS 孤儿行）时自动退回 join 路径。
- **公开资料**：`docs/research/HISTORY-FORMATS.md` §7 已删除来自真实会话的查询原文，
  只保留形态统计与合成查询示例；真实正文/查询/日志只留在 `scratch/S03`。
- **证据**：`scratch/S03/bench-10k-r1.json`（下表）+ probe 的 `100%` 字面匹配用例。

- **机器**：Windows / x86_64；`PROCESSOR_IDENTIFIER = AMD64 Family 25 Model 68 Stepping 1, AuthenticAMD`；
  本地磁盘；release 构建；暖缓存。
- **数据**：全合成 10,000 会话 × 10 条 = 100,000 消息，10,000 个游标，`rowErrors = 0`。
- **导入**：9 个 pass 完整走完（`indexComplete = true`），172.7 s，库 225 MB，约 579 消息/s。

| 中文 FTS · workspace 过滤 | 320.87 | 345.55 | 363.72 | ≤ 1 s |
| 中文 FTS · source 过滤 | 624.37 | 738.08 | 765.22 | ≤ 1 s |
| 中文 2 字 LIKE · 无过滤 | 134.74 | 161.09 | 163.48 | ≤ 1 s |
| 中文 2 字 LIKE · agent 过滤 | 234.83 | 332.06 | 339.17 | ≤ 1 s |
| 中文 2 字 LIKE · workspace 过滤 | 225.25 | 337.95 | 343.16 | ≤ 1 s |
| 中文 2 字 LIKE · source 过滤 | 505.64 | 627.52 | 710.96 | ≤ 1 s |
| 英文 FTS · 无过滤 | 197.81 | 236.06 | 267.92 | ≤ 1 s |
| 英文 FTS · agent 过滤 | 410.05 | 461.22 | 580.64 | ≤ 1 s |
| 英文 FTS · workspace 过滤 | 394.42 | 519.03 | 569.26 | ≤ 1 s |
| 英文 FTS · source 过滤 | 704.66 | **883.07** | 1023.78 | ≤ 1 s |
| 搜索第 2 页（复用游标） | 156.58 | 216.58 | 253.57 | ≤ 1 s |
| `100%` 字面匹配 · 无过滤 | 138.52 | 169.41 | 214.16 | ≤ 1 s |

- 最慢的是英文 FTS + source 过滤（883.07 ms p95，单次最大 1023.78 ms），p95 仍在 1 s 内，
  max 有 2 次越线；它的成本来自
  `message_id IN (SELECT … WHERE source_id=?)` 的每行探测，已从相关子查询
  `EXISTS`（同规模 231 ms vs 112 ms 计数）换成 SQLite 会建 bloom filter 的 `IN`。
- 无过滤路径只扫 FTS 行；过滤路径同样只扫 FTS 行（`session_id` 已在 FTS 行内），再按主键回填
  50 行。回填缺失时退回 join 路径，保证“有 FTS 孤儿行”时不会返回有洞的一页。
- 后台导入时可交互：单个文件的事务有 1.5 s 上限，超大文件切成多个 pass 提交，SQLite 连接
  在文件之间释放；取消在下一行/下一个文件边界生效。

## 独立复核后的补强（第三轮）

回交前又做了一轮只读复核（三个子代理分别看扫描/来源/边界/界面/性能），以下问题被确认并
修复，都补了回归测试（历史模块因此从 80 条增加到 89 条）：

| 问题 | 影响 | 修复 |
|---|---|---|
| 复核窗口用 `size_bytes`（含未提交的残行），块表只覆盖已提交前缀 | 残行起点正好落在 256 KiB 边界时，每 pass 都判定“已改变”并整文件重读，`purgeEpoch` 持续自增 | 复核范围改为 `committed_offset`，尾部半行交给下一次 append |
| Full 重读没有把行号复位到 0 | 头部被改写后，同一批消息的 fallback `sourceKey` 全部平移、message id 变化，跨文件去重失效 | `full` 时 `line_index = 0` |
| 压缩复核被 8 MiB 窗口卡死 | 解压后 > 8 MiB 的 `.zst` 永远 `Deferred`，同 size 同 mtime 的改写永远查不出 | 单文件上限改为 64 MiB，可占满本 pass 的复核预算；超出走物理 size/mtime |
| 每次 append 把 `verifyOffset/verifiedAt` 清零 | 持续增长的文件永远从 0 重新复核，中间块改写看不到 | append 且尾块校验通过时保留已覆盖前缀的进度 |
| 复核冷却期内改 mtime 被直接 Skip | 等长改写 + 改 mtime 在 15 分钟内不会被发现 | mtime 变化一律绕过冷却，直接进入复核 |
| 压缩续读超时被记为 `cancelled` | 用户的“取消”与“本次没读完”混为一谈，来源永远不是 `ok` | 记为 `incomplete`（pass `partial`），不冒充用户取消 |
| 删除文件只删游标，不删派生行 | 删掉的 transcript 的消息/正文/FTS 永久留在索引里 | 新增 `purge_missing_cursors`：同一事务里清理 origins、块表、孤儿消息与游标 |
| 根目录自身没有受保护规则约束，且配置期与遍历期是两份名单 | 根配在 `.password-store`/v4 遗留来源可绕过；`microsoft\credentials` 是死条目 | 配置期改用 `guard`；扫描开始时再按 canonical 组件校验一次根 |
| 行错误只在“当次 pass”存在 | 文件不变、下个 pass 跳过它，状态又变 `ok`/`complete=true`，坏记录永久隐身 | 游标 `error_count` 汇总进 `ScanReport.unresolved_line_errors`，状态保持 `partial` 并给出 `reason: line-errors`；整读时清零 |
| 多文件贡献时 `sourceRef` 指向已被清掉的文件 | 消息存活但来源证据撒谎 | 清理后按剩余 origins 重指 `sourceRef` |
| 重复事件会改写 FTS 正文 | 搜索命中一个打开后正文里没有的词 | 只为新消息写 FTS 行（`messages` 本身是 `ON CONFLICT DO NOTHING`，正文不会变） |
| 状态码取“第一条 issue” | 路径序更早的坏行会把 `unsupported` 降级成可重试的 `io` | 按 `unsupported > access_denied > not_found > io` 取优先级 |

新增回归：边界残留不复读、整读复位行号、append 保留复核进度、冷却期内改 mtime、删除文件
清理派生行、受保护根被扫描拒绝、行错误跨 pass 持续、FTS 与正文一致、错误码优先级。

## 未测项与限制

- **文件监听仍未实现**：只有 30 s 周期补扫，这一轮没有改变。
- **复核有延迟上界**：单文件一个周期 `ceil(size/1 MiB)` 个窗口，语料整体一轮至少
  `ceil(总字节 / 8 MiB)` 个 pass，且文件在 15 分钟冷却期内不重复复核；周期内的改写会被
  发现，但不是“立即”。这是有界复核的固有代价，写成永久能力而不是“只验首尾”。
- **压缩文件的复核上限是 64 MiB（解压后）**：再大的 `.zst` 只能靠物理 size/mtime 与前缀
  hash；这是“整段解码才能比对”的成本取舍。
- **带裁剪行的文件不做块复核**：单行超过 1 MiB 时块哈希与文件字节不再一致，这类文件改用
  size/mtime/前缀 hash，并且已经明确报 `line-too-large`，不会被当成 `ok`。
- **压缩文件续读需要重新解码前缀**：解码成本与已提交长度成正比（受 256 MiB/pass 与时间
  预算约束），真实 `.zst` 历史通常只有几 MB。
- **两个实例共享同一数据根**：`inFlight` 仍可能被后启动的实例清掉（没有跨进程租约），
  数据不受影响。
- **真实副本没有做“追加”场景**：探针按设计不写源目录（`multicli_history_probe` 只读），
  真实副本上的追加会改变受测文件，使“导入前后 hash 一致”不再成立。追加由 4 条合成测试
  覆盖（无 event id、改名、重启、mtime 回拨），格式取自同一批真实副本；如果验收要求真实
  副本追加，需要一份可写的副本并在追加后重新计算基线 hash。
- **FTS 行只为新消息写入**：历史模块自身不会造成缺失（消息与 FTS 同事务），但若外部直接
  删除 `history_message_fts` 行，该消息在重建前搜不到。
- **根目录若位于受保护目录名下会被扫描拒绝**（`.ssh`、`credentials`、`ProgramData`、
  `Windows` 等）。这与配置期的规则一致，但一个此前已配置、路径里恰好含这些名字的来源会
  在升级后报 `access_denied`；需要用户换一个根或改名。
- **未做 S03 发布安装包验收**；实窗滚动/导入中交互由 Sol 下一轮独立执行，本轮的界面结论
  来自 jsdom + 代码审查，不冒充实窗。
