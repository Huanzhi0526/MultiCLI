## 逐项修复

### R2-01 持续追加让旧块复核永久饥饿（P1）

**现象**：约 2.6 MB 的 JSONL，20 条消息已导入；把第 9 条改成等长的 `NEW_SENTINEL`
（首 4 KiB 与末半块不变），随后每个 pass 追加一条约 130 KB 的消息并扫描 15 轮。
新消息都正常导入，但旧块从未被比较，`NEW_SENTINEL` 永远不进索引。

**根因**：复核是导入循环里的一个分支（`Decision::Verify`）。文件每轮都增长时 `decide` 总是
返回 `Append`，`verify_window` 一次都不会被调用。`verifyOffset` 只是被“保留”，没有任何路径
推动它前进；也就是说，真实活跃的历史只有在用户停止写入之后才可能被复核。旧回归
“append preserves verification progress”只断言状态被保留，没有断言它真的前进。

**方案**：把复核从导入循环里拆出来，成为一次 pass 的第二阶段。

- 阶段 1（导入）：新文件、追加、截断、替换；`decide` 只回答 `Full / Append / Skip`。
  长度与 mtime 都未变、且首 4 KiB 前缀哈希仍匹配的文件在这里是 `Skip`——中间字节是否真的
  没变，由阶段 2 用块比较回答；前缀哈希不匹配仍然直接 `Full`。
- 阶段 2（复核）：按**持久化的轮转位置**遍历有游标的文件，每个文件从 `verifyOffset` 取一个
  窗口（预算允许时可用到自己的公平份额），走完整文件回到 0；命中不一致 → 用同一条导入路径
  做事务内整文件重建（purge 只删该文件贡献且再无贡献者的消息）。
- pass 预算为复核预留一段（`VERIFY_RESERVE_MS` = 400 ms，且不超过预算的 1/4），所以导入
  再多也不会把复核挤掉。这是**软预留**：截止检查每 64 行一次，单个文件的事务仍可能越过它
  几十毫秒；`verifyPath:<sourceId>` 存在 `history_meta` 里，重启后从上次位置继续。
- 追加仍然保留复核进度（`verifyOffset.min(committedOffset)`），且写前先比对游标所在块的旧
  哈希（`seed_matches`）；只有这一个块会被重写，因此新追加的字节不会把旧改写“吸收”掉。
- 小预算也能推进：窗口按块对齐并受剩余预算约束；正预算会被抬到至少一个块（256 KiB），
  低于块的预算无法比较任何带哈希的单位，会退化成“永远待复核”。`Deferred` 只表示这个文件
  装不进剩余预算，此时继续尝试更小的文件，而不是结束整段复核。

**检测上界**（固定已提交前缀）：窗口 1 MiB，一次 pass 的 8 MiB 预算按轮转顺序分给文件
（每个文件可用到自己的公平份额）。前缀 P 需要 `ceil(P / 1 MiB)` 次“轮到自己”才走完一个
周期；语料 N 个文件、每 pass 覆盖 K 个时，一个文件在 `ceil(N / K)` 个 pass 内轮到一次，
合计最坏 `ceil(P / 1 MiB) × ceil(N / K)` 个 pass，再加一次 15 min 冷却。冷却对“已完成周期
且之后只追加/未变”的文件同样生效；只有同大小但 mtime 变化的原地改写会绕开它。字节位置不会
因为追加而移动，所以持续追加不改变这个上界。K 取决于文件大小：10k 个十余 KB 的文件在
8 MiB/pass 下一次可覆盖数百个；一个 128 MiB（上限）的压缩文件按 1 MiB 窗口需要 128 次，
预算允许时一个 pass 可推进 8 个窗口。

### R2-02 超过 64 MiB 的压缩历史永远 Deferred（P1）

**现象**：合法的 Codex `.jsonl.zst`，350 条消息、解压后约 70 MB，首轮完整导入；把中间一条
`OLD_SENTINEL` 改成等长 `NEW_SENTINEL`，重新编码并用合法 skippable frame 保持物理大小、
恢复原 mtime。连续 10 轮都是 `complete=true, pending_verification=1, verified_bytes=0`，
正文一直是旧值。

**根因**：复核模型只有“解码后的分块”。压缩流的逻辑偏移不能直接映射到文件偏移，按窗口复核
就必须为每个窗口从第 0 字节重新解码（二次复杂度）。旧实现因此设了 64 MiB 的硬阈值，超过就
无条件 `Deferred`；而 `Deferred` 没有任何后续状态能突破，增加扫描轮次永远没有用。界面上的
“复核继续中”和回交里“每个已提交字节都会在有界周期内被比较”对这类文件不成立。

**方案**：为压缩历史增加**物理层**分块基线，复用同一套有界窗口。

- schema v6：`history_file_blocks` 增加 `layer`（`logical` / `physical`），主键改为
  `(source_id, file_identity, layer, block_index)`；v5 行原样复制为 `logical`。
- 导入压缩文件时，在解码之前顺序读一次原始字节（256 KiB/块）写 `physical` 基线；覆盖长度
  以实际读到的字节数为准并写入 `size_bytes`，因此“解析时基线”和“复核基线”是同一批字节。
- 复核阶段对压缩文件读 `physical` 层，窗口与普通文件完全一致：`start/end` 按块对齐，
  `hash_range` 逐块比对，`Changed` → 整段重解码重建。不关心 zstd 是单帧、多帧还是带
  skippable 填充——任何字节变化都会让某个块不匹配。
- 删掉了 64 MiB 阈值。取而代之的是导入前的诚实上限：物理大小 > 128 MiB 的 `.zst` 在解码前
  返回 `unsupported`（`reason=compressed-too-large`），旧行原样保留。解压后 256 MiB 的
  上限仍独立生效（防解压炸弹）。不存在“导入成功后永远等不到复核”的状态。
- v5 游标没有物理基线：复核阶段发现 `compressed && physical 为空` 时做一次完整重读建立基线
  （只发生一次，测试断言不产生重复行）。

**资源边界**：物理基线是一次顺序读（≤128 MiB，按 256 KiB 检查上限、取消与截止时间）；复核
每次只读一个窗口（≤1 MiB）；解码仍受 256 MiB 解压上限与单文件事务预算约束。超时/取消时不
写入不完整基线（整事务回滚）；超时以可重试的 `io`（`reason=physical-baseline-incomplete`）
上报，不会静默跳过。

## 本轮自查发现并修掉的问题（不在原始两项里）

- **复核写入不得改 `size_bytes`（数据可见性）**：阶段 2 可能复核一个阶段 1 因预算没来得及
  导入的文件；若把列目录得到的新长度写进游标，下一轮 `decide` 会认为“长度一致、已处理”而
  永久跳过新追加的尾部（前缀哈希不含长度，不会自愈）。`set_verify_progress` 现在只写
  `verify_offset` / `mtime_ms` / `updated_at_ms`，长度只由导入写入；新增
  `verification_progress_never_hides_an_unimported_tail` 覆盖。
- **压缩基线读超时现在可见**：`hash_physical` 受物理上限、文件截止时间与取消三重约束；超时
  不再伪装成 “incomplete 但不报错”，而是 `io` + `reason=physical-baseline-incomplete`
  （可重试），旧行保留。
- **预算下限**：正预算抬到至少一个块（256 KiB），避免“预算 < 块 → 永远 Deferred”；
  `Deferred` 只跳过当前文件并继续尝试更小的文件，不再结束整段复核。
- **待复核口径**：改为“有基线且自上次完成复核后被写过”，包含“刚追加、尚未复核”的文件；
  没有块表、注定无法复核的游标不再被永久计入。
- **复核中取消**：pass 记为 `cancelled`，不再以 `ok` 掩盖未走完的复核。
- **复核阶段的重建不重复计数**：`files_done` 不会因一次重建超过 `files_total`。
- **复核阶段的瞬时 IO 错误**：记为一条 issue 并继续复核其余文件，不再把整 pass 打成 error。
- **超大压缩文件的二次报错**：阶段 2 不再为已被阶段 1 拒绝的文件重建基线。

  fixture 覆盖（普通/压缩、单帧/多帧、mtime 回拨、重启），格式取自同一批真实副本；如验收
  要求真实副本追加，需要一份可写副本并在每次操作后重设 hash 基线。
- **压缩基线的读取需要磁盘吞吐**：基线要在一个 1.5 s 的文件事务里顺序读完整个压缩文件，
  128 MiB 上限对应约 85 MB/s；更慢的磁盘上会以 `io/physical-baseline-incomplete`（可重试）
  出现在来源状态里，而不是静默跳过。这是有意的：宁可显示“这条读不完”，也不假装复核在进行。
- **压缩文件每轮变化会整段重解码**：物理基线只能证明“字节变了”，重建仍要解码整段。持续
  增长的 `.zst` 每个 pass 都会走一次 Full（受 128 MiB 物理 / 256 MiB 解压上限与 1.5 s 文件预算约束）。
  这与 R1 的行为一致，本轮未改。
- **物理大小 > 128 MiB 的压缩历史被拒绝**：这是有意的硬上限（导入前 `unsupported`，旧数据
  保留）。解压后 > 256 MiB 同样拒绝。
- **复核周期仍与语料规模成正比**：窗口成本是文件实际字节数，不是一个固定 1 MiB。10k 个
  十余 KB 的文件、8 MiB/pass 时一次 pass 可覆盖数百个，完整扫一遍是数十个 pass；只有接近
  上限的单个大文件才会退化成 `ceil(size / 1 MiB)` 个 pass。这是预算换低干扰的取舍，不是遗漏。
- **头部每轮被改写的大文件无法越过单文件读取预算**：首 4 KiB 变化会让 `decide` 走 `Full`，
  而单文件单 pass 只读 32 MiB，所以一个每轮都重写第一行、再追加的 100 MB 文件会一直从 0
  重读，32 MiB 之后既进不了索引也进不了复核。这是 R1 的 Full 语义，不是本轮引入；真实 CLI
  不会每 30 s 重写首行，但它属于已知边界。
- **超过 32 MiB 的文件被判定改写时**，重建在同一事务里先清旧行再分多个 pass 重新导入；追平
  之前它的尾部不在时间线与搜索里（`complete=false` 会标出未完成）。复核现在也会触发这条
  路径，属 R1 既有语义。
- **两个实例共享同一数据根**时 `inFlight` 可能互相清除（R1 已登记，本轮未变）。
- **未做 S03 发布安装包验收**；真实界面与剩余真实历史由 Sol 在阻断解除后独立执行，本轮的
  界面结论来自既有 jsdom 回归（本轮未改前端）。
