## 实现结果

### 1. 版本化签名与有界安装扫描

- `signature.rs`：`SIGNATURE_SCHEMA_VERSION = 1`，注册表固定 3 条签名（Codex CLI / Claude Code / CodeBuddy Code）。每条给出产品、原生 exe 名、shim 名、Node 包入口后缀、可信安装根、残留目录、结构性 flag、cwd flag、版本标记、来源与正反样本。其余六族留给 S06，未声称支持九族。
- `check_samples` 在单元测试里跑完 18 条正反样本；`node -e ...`、`cmd /c echo codex`、`python codex_helper.py`、`C:\Users\me\Downloads\codex.exe`、`codex-code-mode-host.exe`、`claude-code-tools\cli.js`、`README.md` 均不匹配。
- `detect.rs`：只扫 `PATH`（≤64 个目录，非递归）与签名声明的安装根。实测本机得到：Codex `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`、Claude `%USERPROFILE%\.local\bin\claude.exe`、CodeBuddy `%APPDATA%\npm\codebuddy.cmd`→`node_modules\@tencent-ai\codebuddy-code\bin\codebuddy`。
- 去重按"包入口 canonical 路径"（Node）或"canonical exe"（原生）做，`codebuddy.cmd` / `.ps1` / `cbc.cmd` 三个 shim 只产生一条安装；名字优先 `codebuddy`（主名）而非 `cbc`（别名）。
- `%APPDATA%\npm\node_modules\@openai` 这类空目录只报 `historical-residue`；`missing-target` 的 shim 不会被升级成"已安装"。目录存在本身从不等于已安装。

### 2. 受限包装器解析与超时探测

- `wrapper.rs` 把 `.cmd/.bat/.ps1` 当数据读（≤64 KiB）：只展开 shim 自身目录变量（`%~dp0`/`%dp0%`/`$basedir`/`$PSScriptRoot`），`%USERPROFILE%`、`%TOKEN%`、`$env:API_KEY` 原样保留不解析；取最后一条 `node <entry>`；入口必须位于 shim 目录内、存在、且是 `.js/.mjs/...` 或带 node shebang；否则 `missing-target` / `unsafe-wrapper` / `not-node-entry`。从不执行 shim，也不起 `cmd.exe`/PowerShell。
- `probe.rs` 只在入口已可信时探测：argv 数组直启、`CREATE_NO_WINDOW`、8 秒超时（超时只 kill 自己的子进程）、输出上限 8 KiB、5 分钟缓存。版本解析要求产品标记（Codex 需 `codex-cli`、Claude 需 `Claude Code`），失败保留 reason，不变成"未安装"。
- 实测版本：Codex `0.166.0`、Claude `2.1.153`、CodeBuddy `2.179.0`，与 `--version` 输出一致。

### 3. schema v3 与安装身份

- `SCHEMA_VERSION = 3`。v3 迁移重建 `agent_installations`，新增 `executable_identity` + `executable_identity_kind`，唯一键改为 `(host_id, agent_id, config_profile_id, executable_identity)`；同时新建 `discovery_processes`。
- 重建使用 `PRAGMA foreign_keys = OFF` + 事务 + 提交前 `pragma_foreign_key_check`，失败整体回滚并恢复 FK；旧行 id、Run/Capability 外键、备注/标签、Session/Message 全部按原值复制。缺 canonical 的旧行写入 `unresolved-display:<display path>`，不猜真实路径。
- 版本不是身份：`register_discovered_installation` 用确定性 id（host+agent+profile+identity 的 128 位 FNV），重复发现幂等；版本变化不新增行。
- 配置 profile 未取得时统一写 `unconfirmed-local`，视图单独给 `configProfileStatus: "unconfirmed"`，不伪称 `default` 或当前账号，也没有把 exe 拼进 profile。

### 4. Windows 只读进程快照与身份状态机

- `winproc.rs`：`HostBackend` 接缝（enumerate / inspect / resolveExecutable）。镜像路径用 `QueryFullProcessImageNameW`，创建时间用 `GetProcessTimes`，argv 用 sysinfo 的进程命令行；**不**读环境、PEB 工作目录、内存或凭据。
- `creationTime` 为 UTC ISO-8601、**7 位小数（100 ns）**，例如 `2026-11-01T18:28:39.0838233Z`；取不到就 `identity = null` 的未确认候选，不造稳定身份。
- `snapshot.rs` 状态机：同身份幂等合并；PID 复用（创建时间被验证变化）→ 旧行 `exited/pid-reused`，新行独立；PID 消失 → `exited/process-ended`，保留 20 代后收敛；权限不足/本代次未能重识别 → `unknown`，不判退出；整次枚举失败 → 全部 `stale`、状态不变、`lastSuccessAt` 不前进；下次成功恢复 `fresh`。
- 父链只在父身份与创建时间都可验证且父不晚于子时成立，否则 `parent-not-found` / `parent-unverified` / `parent-newer-than-child`。OS 父子不等于委派，也不等于同一 Session。
- 后台线程默认 3 秒采样（设置 1–60 秒），安装探测独立缓存；手动刷新合并在途扫描，不并行开第二个扫描器；`RunEvent::Exit` 时结束自有线程，从未 signal/attach/kill 外部进程。

### 5. 识别、树与关联

- `classify.rs` 三级识别：已验证安装入口（`installation-exe`）→ Node 包入口（`node-package-entry`）→ 可信目录 + 同名 exe（`path-entry+filename`，`likely`）。品牌词只出现在 argv[1] 的入口位置才有意义，后续参数（提示词、`echo` 文本、URL）一律不看。
- 进程的 `entryKind` 表示**本次进程**的进入方式（原生镜像 / Node 入口），不是安装的常用入口形态；cmd/ps1 包装器不会与它启动的 node 运行时各算一份实例。
- 工作区只在 CLI 带显式目录参数（目前仅 Codex `-C/--cd`）且该目录已登记为 workspace 时关联，证据 `explicit-directory-argument`；其余一律"未关联"，不默认绑定 MultiCLI 当前项目。
- 无 cwd 的外部 CLI 照常可见；本阶段不创建 Session/Run（`sessionId` 恒为 null），理由：`Run.transport` 冻结取值没有"未连接观察"，写任一值都是伪造协议。
- 脱敏：DB/IPC/错误/日志/诊断只保留入口 basename、声明过的结构性 flag、`<value>` 与 `<n withheld>`。实测 `node.exe --serve <5 withheld>`，端口、密码、模型名、URL、路径都不出现。

### 6. 产品 IPC、只读 UI 与设置

- 注册三个发现命令 `multicli_list_installations` / `multicli_list_processes` / `multicli_refresh_discovery`，外加一个有界设置命令 `multicli_update_discovery_settings`（见"接口变化"）。
- 游标带代次：进程游标绑定 `scan.generation`，安装游标绑定安装集 `epoch`（只在安装集变化时 +1）。跨代次返回 `conflict` + `{stage:"cursorGeneration", cursorGeneration, currentGeneration}`，显式失效而不是静默漏/重。
- 顶部新增「会话 / 安装 / 外部进程」三个页签；S01 三栏导航原样移到 `SessionBrowser.tsx`，testid 与行为不变。安装页显示状态/入口/版本/版本来源/探测时间与原因/未确认 profile/发现来源；进程页显示 state × freshness 两个独立徽标、身份三元组、来源程序与父进程、未关联工作区、脱敏命令、首次/最近发现。外部进程**没有**发送、接管、kill 或伪终端按钮。
- 扫描失败显示真实 `AppError`（`io` / `access_denied` 等）与重试；整次失败保留旧行并标"过期"，不显示为空列表。页脚常驻采样说明（"短于扫描间隔可能漏见，不是审计级全量"）。

- **安装身份与 Codex 布局**：原生入口的 identity 是其 canonical 目标。Codex 的入口是应用执行链接，目标含版本目录，升级后会生成新 identity。若要在升级后保持同一安装行，需要把原生 identity 改为"入口路径"并把 canonical 目标只用于进程匹配；这会改动卡里"优先真实 canonical executable"的措辞，留待主管决定。
- **进程 `entryKind` 语义**：表示该进程本次的进入方式（native-exe / node-package），与安装的常用入口形态（例如 codebuddy 的 `cmd-wrapper`）分开。旧构建写入的 exited 行可能仍是 `cmd-wrapper`，属历史数据。
- **游标跨代次失效**：进程列表默认 3 秒一代，用户停在第二页时前端暂停自动刷新；跨代次继续分页会得到 `conflict`，需重载第一页。这是刻意的"明确失效"而不是静默漏重。
- **轮询频率**：进程页按扫描间隔的一半（≥1 秒）重读第一页，每次只是内存快照的 IPC 读，不触发扫描；这是把"发现 → 显示"的额外延迟压到半个间隔的手段。
- **`scripts/multicli/verify.ps1 -Scope Test` 的环境依赖**：本机 Windows PowerShell 5.1 会把 cargo/vitest 的 stderr 当终止错误，`corepack pnpm exec vitest` 在本机 PATH 下也找不到 `node_modules/.bin/vitest`。Rust/Test scope 因此用仓库内既有的便携 PowerShell 7.4.6 运行，Test scope 额外把 `node_modules/.bin` 前置到 PATH。这是环境问题，未改脚本（脚本改动不在授权范围）；若主管希望固化，建议在 `enter-env.ps1` 里补 `node_modules/.bin`。
