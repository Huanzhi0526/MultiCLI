## 实现结果

### 1. 用户可观察到的行为

- 顶部新增「历史」页签（`view-history`），三栏：来源 / 搜索与浏览 / 会话详情。来源必须由用户显式添加（候选下拉或手填绝对路径）；没有首次启动自动遍历。
- 来源卡片显示产品、启用状态、真实索引状态徽标（`idle/indexing/ok/partial/error/cancelled`）、代次、文件进度、已索引消息数、最近尝试/最近成功、真实 `AppError` 与重试。启用/禁用、刷新、重建（二次确认）都只影响本来源派生索引。
- 搜索在 SQLite 完成：≥3 字符走 FTS5 `trigram`，1–2 字符/单汉字走转义 `LIKE`；支持 `agentId`/`sourceId`/`workspaceId` 过滤与稳定游标。结果片段是纯文本，命中词窗口两侧带省略号。
- 点搜索命中会用 `anchorMessageId` 打开**同一个** Session 与同一条 Message：消息页从锚点前 `limit/4` 条开始，锚点行高亮并滚动到视口中央，底部可继续按游标加载。
- 会话详情显示 Session（含 `origin=history-only`）、工作区（primary/related + 证据）、Run 计数、消息条数与 kind 分布、首末消息时间、来源证据（sourceIds/文件数/parser 版本/`readOnly`）。不附全量消息。
- 消息按 `(observedAt, seq, id)` 升序；工具调用展示工具名与输入（折叠），未知字段只显示**字段名**（折叠、脱敏），超长正文折叠展开。
- 「检查继续目标」只解析：`resolved / blocked / unknown / unsupported` + 固定 reason + 冲突列表 + 证据；执行按钮始终禁用并注明 S05。

### 2. 来源配置、身份与增量事务

- 来源：`history:<agent>:<product>:<configProfile>` 命名空间；`(sourceNamespace, nativeId)` 是原生会话唯一身份，Session id 为 `hist-` + SHA-256 前 40 hex，跨文件、跨 pass、跨重启稳定。
- 根边界：绝对路径、存在、可读、目录；拒绝盘符/UNC 根、用户 profile 根、`%APPDATA%` 本身，以及任意层级的凭据/系统目录名（`.ssh`、`.gnupg`、`.aws`、`.kube`、`credentials`、`Windows`、`Program Files`、`ProgramData` 等）。扫描时跳过符号链接/重解析点。
- 同一 `(host, agent, profile, canonicalRoot)` 幂等；已存在 sourceId 换根返回 `conflict`，不静默改挂。
- 文件身份是**路径 hash**，不是内容 hash：追加写不会让游标失效。替换/同 size 重写由「前缀 hash（前 4 KiB）+ 已提交末尾锚点 hash（4 KiB）」识别；任一不符即整读。
- 每个文件的导入与游标推进在**同一事务**内；整读时先在同一事务内清旧派生行，失败整体回滚，不会留下半个文件。
- 单条记录在 savepoint 内写入；被拒绝的一条（例如工作区在 stat 与插入之间消失）不会留下消息、来源行、FTS 行或空会话。
- 未完成尾行不入库，游标停在最后一个换行之后；补齐后只导入新增行。
- 坏行记 `invalid-json` + 行号后继续；>1 MiB 的单行导入 `recordType:"oversized-line"` 隔离标记并记 `line-too-large`，不丢整个文件。
- 轮转：`session.jsonl.<1-3 位数字>` 分片按同一产品格式读取，路径身份独立，主文件重写不会清掉分片；重叠事件按 `sourceKey` 去重。
- 后台单线程、单 pass 顺序执行；刷新/重建合并在途请求而不是开第二个扫描器；取消是协作式，只在行/文件边界停，已提交部分保留。

### 3. 三核心格式映射

详见 `docs/research/HISTORY-FORMATS.md`（含版本、逐类型处理、未映射项）。要点：

| 产品 | 版本 | 身份 | 主要记录 |
|---|---|---|---|
| Codex CLI | 0.166.0 | `session_meta.payload.session_id`，缺失取文件名 UUID | `response_item`（message/function_call/tool output/reasoning/compaction）、`event_msg`、`compacted` |
| Claude Code | 2.1.153 | 每行 `sessionId`，其次文件 stem | `user/assistant`（text/thinking/tool_use/tool_result/image）、`system`、`attachment`、`summary`、`ai-title` |
| CodeBuddy Code | 2.179.0 | `sessionId` / `session-meta.id` | `message`、`reasoning`、`function_call`、`function_call_result`、`summary`、`ai-title` |

- 三套 parser 各自实现 `HistoryParser`，不共用 Codex 映射再换产品名。
- 时间统一 UTC 毫秒 ISO；无原生时间用文件 mtime 并在 `content.timeSource="file-mtime"` 明示。
- 标题优先级 `native-title` > `first-user-message` > 空；原生标题会替换先前的首条消息猜测，反之不会。首条用户消息是 XML 标签形态的注入上下文时跳过。
- 未知字段只保留字段名（≤40 字符、受限字符集、最多 32 个），从不保存值；`authorization`、token、cookie 等值不会进入数据库、日志或 UI。
- 历史会话 `origin=history-only`，没有 Run；不伪造 native/acp/pty 连接。

### 4. 搜索与有界读取

- FTS5 表是普通表（非 external-content），`tokenize='trigram'`；查询包成双引号短语，内部 `"` 双写，FTS 操作符按字面处理。
- 短查询（1–2 字符）对 `body` 做 `LIKE ... ESCAPE '\'`，转义 `% _ \`，查询与正文都小写化；`100%` 这类输入不会变成通配符。
- 片段在 Rust 侧按字符窗口生成（前 60 / 后 120 字符），去控制字符与 bidi 覆盖符；不使用 FTS `snippet()`，UI 只按文本渲染。
- 搜索排序 `session.createdAt DESC, observedAt ASC, seq ASC, id ASC`；游标带排序名，跨列表/非法编码返回 `invalid_argument`。
- `multicli_get_session_metadata` 不附消息；`multicli_list_session_messages` limit 1..200，`cursor` 与 `anchorMessageId` 互斥，锚点不存在返回 `not_found`。
- 保留 S01 的 `get_session` 兼容接口，历史 UI 不调用全量详情。

### 5. 继续目标（只解析）

- 判定顺序：活跃 Run（starting/running/stopping）→ `blocked` + `active-run`（最强确定性结论，优先于其他状态）；无 nativeId → `unsupported` + `missing-native-id`；无对应产品 → `unsupported`；同产品存活实例 → `unknown`（同工作区时附 `live-external-process`，否则 `live-process-unlinked`）；无已确认安装 → `unknown`；其余 `resolved`。
- 不用“没匹配到进程”证明空闲；不把同产品任意进程当成同一会话；`executionAvailable` 恒为 false；不 spawn、不发 prompt、不写 CLI 文件、不建 Run。

### 6. schema v4

- `SCHEMA_VERSION = 4`，新增 `history_sources`、`history_index_state`、`history_cursors`、`history_message_origins`、`history_session_facts`、`history_message_fts`，不改既有表/ID/外键。
- 迁移沿用既有版本化备份 + 单事务；v1/v2/v3 → v4 连续升级，任一语句失败整体回滚。
- 重建只清本来源独占的派生行：`messages`（同一条消息若仍被其他来源引用则保留）、origins、cursors、FTS；Session id、用户备注/标签、S02 安装/进程观察不动。

## 性能

- **机器**：Windows / x86_64；`PROCESSOR_IDENTIFIER = AMD64 Family 25 Model 68 Stepping 1, AuthenticAMD`（该变量未给出具体型号）；本地 SSD/磁盘（未单独采集磁盘型号）；release 构建；暖缓存。
- **数据**：全合成 10,000 会话 / 100,000 消息（每会话 10 轮），10,000 个游标，`rowErrors = 0`，文件数/会话数与生成数一致。
- **导入**：9 个 pass 完整走完（`indexComplete = true`），177.2 s，库 199 MB，约 564 消息/s。基准把单 pass 预算显式设为 20 s；产品默认增量预算 4 s、重建 30 s。
- **采样**：每用例 3 次预热 + 30 次采样；p95 用 nearest-rank（`ceil(0.95×30)−1`，即第 29 个样本）；计时覆盖一次同步 service 调用（SQL + 结果映射），**不含** IPC 与 React；搜索结果上限 50。
- **最坏情况而非抽样**：合成正文每条都含 `历史记录` / `recorder`，三个搜索各自命中全部 100,000 条、各只返回 50 条（JSON 的 `observed` 段记录了 `total/returned/matchMode`）。这不是“挑一个稀有词”的数字。
- **会话时间**：每个会话的 `created_at` 取该会话第一条记录的时间，10,000 个会话不再共用来源时间，`sessionCreatedAt DESC` 这一排序键被真实拉开。

| 用例 | p50 (ms) | p95 (ms) | max (ms) | 目标 |
|---|---:|---:|---:|---|
| `listSessions`（50 条） | 2.83 | 3.59 | 3.71 | ≤ 1 s |
| 中文 FTS（命中 100,000，返回 50） | 225.72 | 274.16 | 283.61 | ≤ 1 s |
| 中文 2 字 LIKE（命中 100,000，返回 50） | 207.46 | 254.07 | 270.53 | ≤ 1 s |
| 英文 FTS（命中 100,000，返回 50） | 299.93 | 363.61 | 411.13 | ≤ 1 s |
| `messagePage`（会话 10 条，上限 50） | 0.24 | 0.32 | 0.32 | — |

- 中文回退没有拖慢：2 字查询的 p95 低于 3 字 FTS（254 ms vs 274 ms），因为两者都只取 50 行，差别在匹配阶段。
- 背景：无过滤搜索只查 FTS（计数 11 ms，取 50 个 id 后按主键回填）；过滤搜索仍走 join，若过滤后仍命中全部消息会退回到“计数 + 取页各一次 join”（约 1.3 s），属于已知上限，见“未测项与阻碍”。
- 索引耗时随规模近似线性（约 177 s / 10 万条、1.8 ms/条），主要成本是每文件一个事务与 FTS trigram 写入；没有做批量提交，因为半导入回滚比导入速度重要。

## 审计跟进（子代理独立走查后修复）

- **resume 判定顺序**：`blocked`（活跃 Run）现在优先于 `unsupported`/`unknown`，契约 §5 同步改写；不再出现“无 nativeId 但有写入租约却报 unsupported”。
- **重启残留 `inFlight`**：历史引擎启动时清掉本机来源的 `in_flight=1`，状态记为 `cancelled` 并保留“下一 pass 从已提交游标继续”的说明；不再永久显示“索引中”。
- **不覆写 S02 身份**：历史来源注册 agent 改为 `ON CONFLICT DO NOTHING`，不会用硬编码 vendor/displayName 覆盖 S02 探测到的真实值。
- **partial 错误码**：按第一条 issue 映射 `unsupported/access_denied/not_found/io`，格式不符不再被压成可重试的 `io`。
- **路径大小写幂等**：来源存在性比较用折叠路径，Windows 下同一根不同大小写返回原来源而非 `conflict`。
- **根可读性前置**：保存来源时真的列一个条目，不可列返回 `access_denied`，不拖到索引时才失败。
- **控制字符/双向覆盖**：正文、工具输入/参数、会话标题统一 `sanitize_text`；新增测试断言 ESC/U+202E 不落库。
- **列目录不计入解析预算**：10k 文件的根不再把 4 秒预算耗在 `read_dir` 上；同时把 10k 次游标查询合并为一条，避免导入推进被拖垮。
- **按片段推进**：扫描从上次报告的 `nextIndex` 开始并循环到列表末尾，预算用尽就报告下一段起点。否则每 pass 都从 0 重查前缀，10k 文件会退化成“永远导不完”。新增回绕测试。
- **FTS 删除不再全表扫描**：`message_id` 是 UNINDEXED，原来的“每条消息先 DELETE 再 INSERT”在 10 万行时是二次复杂度，导入从 777 文件/pass 掉到 151。新消息不再删除，只有已存在消息才删；重建改为 400 条一批删除。
- **搜索不再对全部命中做两次 join**：10 万条全部命中时，计数 join 620 ms、取页 join 655 ms。现在 FTS 行内冗余 `observedAt/seq/sessionCreatedAt`，无过滤搜索只用 FTS 计数与 `LIMIT`，再按主键回填 51 行；过滤搜索保留 join 路径。回填缺失时自动退回 join，避免 FTS 孤儿行造成空洞分页。
- **会话创建时间**：原来所有历史会话都写来源配置时间，导致 `sessionCreatedAt` 相同、排序退化。现在取该会话第一条记录的时间；FTS 排序键也改用**已存储**消息的 `observedAt/seq`，重复导入不会让 FTS 与 `messages` 排序分叉。
- **不可读目录不再触发游标清理**：`collect_files` 区分“达到上限截断”和“有目录读不了”；后者会阻止 `complete=true` 与按列表清理游标，避免临时 ACL/离线目录把整段历史游标删掉。
- **native 标题也脱敏**：Claude/CodeBuddy 的 `aiTitle` 走统一 `native_title()`，控制符与 bidi 覆盖符不再进入会话标题；例行跳过的符号链接不再记为 issue，避免每次 pass 被误判 `partial`。
- **UI 状态**：补 `historyStale` 三语文案；搜索失败不再同屏显示“0 条结果”；来源列表补 `error-more`；来源状态轮询失败显示“状态未知”；候选目录显示缺失/不可读原因；进度条有 `role=progressbar`；`complete=false` 显示“本 pass 未走完”；`ResumeBlock` 增加迟到响应保护；消息正文不再整对象 JSON 化（避免把未知字段值带出来）。
- **未采纳**：`SourcesPanel` 的候选下拉仍是“选完回到占位项”的一次性选择器（无状态副作用），未改为持久选中；属交互偏好，不影响语义。

## 未测项与阻碍

- **NOT_RUN：SQLite 型历史源**。本机三款产品的历史都是 JSONL（CodeBuddy 的 `sessions/*.json` 是运行态，不是会话正文）。没有观察到 SQLite 历史库，因此没有实现/验证“只读连接 + WAL 一致性快照”路径。若后续产品改用 SQLite，需要单独的有界只读连接实现，当前代码不会误把它当 JSONL。
- **NOT_RUN：真实 GUI 手工走查**。本阶段用 jsdom + FakeApi 覆盖 UI 状态与交互；没有启动打包后的 Tauri 窗口做人工点击。滚动定位在 jsdom 中不可用（`scrollIntoView` 为空操作），只验证了锚点高亮与锚点参数，真实滚动效果属于未测项。
- **NOT_RUN：Codex 之外产品的压缩历史**。只有 Codex 观察到 `.jsonl.zst`；Claude/CodeBuddy 的压缩形态未观察到，也未实现。
- **限制：轮转分片从中途开始**（没有会话头）会以 `unrecognized-format` 报告，不并入无关会话；这是有意的保守行为。
- **限制：文件监听未实现**。仅 30 秒周期补扫 + 显式刷新；短于间隔的新写入会晚一个周期出现，不是实时 tail。
- **限制：单文件单 pass 32 MiB、单 pass 4 秒**。超大文件需要多个 pass 才能追平，`complete=false` 会明示。
- **限制：搜索短词回退是 `LIKE` 全表扫描**（仅 1–2 字符）。10 万消息基准的 p95 见性能段；更大数据量需要另行评估。
- **限制：带过滤的宽泛搜索仍走 join**。无过滤路径已优化到 p95 ≤0.42 s；若同时带 `agentId/workspaceId/sourceId` 且查询命中全部 10 万条，会退回到约 1.3 s。过滤通常用于收窄结果，但这不是硬保证。
- **限制：替换检测是双窗口**（前 4 KiB 前缀 + 已提交末尾 4 KiB 锚点）。对大于 8 KiB 的文件，若同 size、同 mtime 且只有中间字节被改写，会被判为未变化；这是有意的成本取舍，测试覆盖的是小文件同长度改写与常规截断/替换。
- **限制：两个应用实例共享同一数据根时**，后启动的实例会清掉先启动实例的 `inFlight` 标志（数据库里没有跨进程租约）。数据不会损坏，只是状态显示可能短暂不准。
- **限制：FTS 行与 messages 同事务维护**；本阶段没有删除会话的产品路径。若外部工具直接删 `messages`，会留下孤儿 FTS 行；无过滤搜索检测到回填缺失时会自动退回 join 路径，`rebuild` 也会清除。
- **与 S03 无关的既有问题**：`cargo check --examples` 会在基线已有的 `examples/ops_smoke.rs` 报 6 个 `impl Future` 错误（该文件在 `f7f377dfb` 后未改过，也不在 `verify.ps1` 范围内）。S03 的两个 example 单独 `cargo check --example` 通过。
- **限制：继续目标不判断“空闲”**。S02 进程没有 native session id，只能给出 `unknown` + 解释；真正执行与强互斥留给 S05。
