## 3. 协议方法与能力记录（去敏）

完整报文见 `docs/contracts/runtime-v1.md` §6，原始帧留在 `scratch/S05/`。摘要：

### 3.1 Codex app-server（`OBSERVED`，握手与轮次生命周期）

`initialize` → `initialized` → `thread/start|thread/resume` → `turn/start` → `turn/interrupt`。
服务端通知：`item/agentMessage/delta`、`item/reasoning/*Delta`、`item/started|completed`、`turn/started|completed`、`error`。
审批请求：`item/commandExecution/requestApproval`、`item/fileChange/requestApproval`（以及旧版 `execCommandApproval` / `applyPatchApproval`）。
应答统一 `{"decision": …}`：新式为 `accept` / `acceptForSession` / `decline` / `cancel`，旧式为 `approved` / `denied` / `abort`。

**关键判据**：`decline` 只结束该次调用、回合继续；`cancel` 会中断整个回合。两者是两个独立按钮，未合并。

**未走到的部分**：本机无法到达 Codex 模型端点，任何真实回合都在约 200 s 后以
`turn/completed{status:"failed", error.message:"workspace routing discovery timed out"}` 结束，
期间捕获到 `error{willRetry:true, "Reconnecting... 2/5"}`。**审批应答一帧都没有发出过。**

### 3.2 Claude Code（`OBSERVED`，含完整权限往返）

一个进程服务多轮（`result` 之后仍等 stdin，关闭 stdin 才退出；两轮同 session 实测 exit 0）。
`--session-id` 必须是全新 UUID，回到既有会话只能用 `--resume`。

权限往返（`--permission-prompt-tool stdio`，该参数不在 `--help` 里但被接受）：

```
← {"type":"control_request","request_id":"<uuid>","request":{"subtype":"can_use_tool",
     "tool_name":"Write","input":{…},"tool_use_id":"call_…"}}
→ {"type":"control_response","response":{"subtype":"success","request_id":"<uuid>",
     "response":{"behavior":"allow","updatedInput":{…}}}}      // 允许，updatedInput 必填
→ {"type":"control_response","response":{"subtype":"success","request_id":"<uuid>",
     "response":{"behavior":"deny","message":"…","interrupt":false}}}   // 拒绝
```

`allow` 缺 `updatedInput` 会被 CLI 的 schema 拒绝，并以普通 `tool_result`（前缀
`Tool permission request failed`）回给模型，模型于是换工具重试：实测一次坏帧产生 5 次额外请求、
成本翻倍，而 `result` 仍是 `success`。本适配器把该前缀识别为客户端契约错误并立即熔断。

取消：客户端发 `control_request{subtype:"interrupt"}`，回合以 `result.subtype=error_during_execution` 结束。

### 3.3 CodeBuddy ACP（`OBSERVED`：initialize / session.new / load / resume；正文与权限 `NOT_RUN`）

`initialize{protocolVersion:1}` → `{protocolVersion:1, agentCapabilities{loadSession:true,…}, authMethods[…]}`；
`session/new{cwd, mcpServers:[]}` → `{sessionId, models, modes, configOptions}`；
`session/load|resume{sessionId, cwd, mcpServers:[]}`（**cwd 与 mcpServers 必填**，缺一即 `-32602`）；
`session/prompt{sessionId, prompt:[…]}`；`session/cancel{sessionId}`。

失败形态不是 JSON-RPC error，而是 `result.stopReason="refusal"` + `result._meta["codebuddy.ai/errorMessage"]`（内嵌 JSON 字符串）。
本机独立启动的 CLI 没有登录态，实测得到 `Authentication required`。

## 4. 公共状态机与进程/资源归属

- **Run**：`starting → running → stopping → exited|failed`；终态不可重开（DB 层同样约束）。
- **一轮 = 发送即开始**：Claude 没有"回合开始"帧，所以发送时就建立 running 的 turn；`turn/completed` 按"当前运行的 turn"关闭，不只按 id 匹配。
- **交互态**：`awaiting-permission` 只由真实 pending 请求产生；`working` 只由协议消息产生；静默不推断 `idle`。
- **事件**：seq 只在 `(runId, streamId)` 内单调；`nativeEventId`/`sourceKey` 幂等；未知事件以 `protocol/unknown` 保留并计数；日志上限 4000 条 / 4 MiB，超限前移 `droppedBefore` 并置 `journalTruncated`。
- **通知**：`multicli://runtime` 只推 `{runId, seq, …}`，前端按 runId 拉 `runtime_get`（80 ms 去抖），不把正文塞进 IPC 队列。
- **进程归属**：子进程加入 kill-on-close Job，失败即放弃启动；身份 `hostId+pid+creationTime` 在 spawn 后立即捕获；只有本应用创建的进程可结束，没有按 PID 接管的入口。
- **终态持久化**：进程自然退出、被结束、适配器报错三条路径都写一次 Run 行（`terminal_persisted` 只允许写一次）。

### 4.1 工具：双账本三字段

**"没有权限请求"不等于"被拒绝"**。Claude 在默认模式下对读操作与项目内编辑**静默执行**。
每个工具携带 `authorization`（`not-requested|pending|allowed|allowed-always|denied|auto-denied`）、
`execution`（`unknown|running|executed|not-executed`）、`outcome`（`unknown|ok|failed`）三个互不折叠的字段，
`quadrant()` 派生出 8 格，其中 `never-asked-executed-failed` 必须能在界面上直接看出。

`is_error` 只作原文回显，不参与判断：Claude 全量 `tool_result`(n=15) 显示成功侧按工具确定性地不同
（`Write` 3/3 不带该字段，`Bash` 1/1 显式 `false`），失败侧同一个 `true` 覆盖五种无关成因。

轮次结束时仍 `running` 的工具落为 `execution=unknown` 并计入备注，不留永久未完结的账本。

## 6. Session / Run / native_id 对照

- 新建：Session(`source_namespace = "<agent>:runtime:local-windows"`, `origin=managed`) + Run(`starting`) 先落库，再 spawn。
- handshake 取得 native id 后写回 Session；若 Session 已有不同 native id 则拒绝覆盖并记备注。
- 继续：**同一 Session**、**新 Run**；继续前用 S03 的目标/冲突解析，`blocked` 直接拒绝，`unknown` 继续但写明原因。
- 关闭窗口到托盘后结构化连接继续；显式退出时 `stop_runtime()` 先结束自有连接再结束终端。
- 非 managed 不可停止：没有任何入口接受外部 PID。

实测（Claude）：两次 Run 的 `session_id` 相同、`nativeSessionId` 相同、`run_id` 不同，DB 两行均在。

## 8. PTY fallback

结构化 Run 与 PTY Run 是两条独立路径，互不冒充：

- 结构化界面只读协议帧，从不解析终端字节；PTY 页面仍是 S04 的 `TerminalWorkspace`。
- 结构化连接失败不会自动降级成 PTY；用户要终端时显式切到"终端"页。
- 反向也成立：PTY 输出不会进入结构化消息流，`interactionState` 不会被终端字节推断。

1. **Codex 权限往返未实测**：网络阻塞（见 §5.2）。协议面已按 schema + 两条独立探针核对，但没有发过一帧应答。

5. ACP stdio 仍会绑定本地 HTTP 端口并改写 `~/.codebuddy/web-ui-port.json`（CLI 自身行为，本应用不写该文件）。
6. 同一 Session 的并发第二 Run 被拒绝（`conflict`），不做自动接管或迁移。
7. 结构化运行上限 8 个；权限等待默认 300 s，超时按该请求自己的 deny 选项回送并记 `expired`。
8. Codex 的 `serverRequest/resolved`：静态确认存在（`ServerNotification.json`），运行时 **未观测到**，未用于状态推进。
9. CodeBuddy 的 `permissionResolved` 无请求级 id，不能作为单个请求的回执，未用于状态推进。
