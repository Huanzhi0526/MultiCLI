## 2. F01：恢复提交点与失败语义

修复后的顺序：

1. 再次校验快照（SHA-256、完整性、schema 不降级、文件在 `backups/` 内且非链接）。
2. 把当前 `multicli.db` 与 `-wal/-shm` 复制到 `backups/pre-restore-<stamp>-<id>/`。
3. 把旧 `-wal/-shm` **移动**到同一目录（不是删除）；任一步失败移回。
4. 把 staging 快照 rename 为 `multicli.db`。
5. 写 `last-restore.json`（提交点）。写失败：把新库移到 `applied-new.db`，把旧副本 rename 回原位，移回
   sidecar，返回 `io`；**此时旧行仍在**。
6. 删除 `restore-pending.json`；删不掉也不重放：`pending_restore` 只在 `last-restore.json` 的
   `planId` 与当前计划严格相等时返回 `None`，不再用墙上时钟比较；`restoredSha256` 只作第二道校验。
7. `MultiCliRuntime` 增加 `restore_attempted` 门闩：服务错误重试、数据页刷新不会在当前窗口提前执行；
   只有进程启动后的第一次 `service()` 尝试。

新增/保留回归：

- 主管 `restore_reporting_failure_must_not_silently_replace_current_rows`：5/5 通过。
- `a_completion_metadata_failure_rolls_back_instead_of_claiming_success`：完成记录失败后旧行保留、
  pending 可重试、`last_restore` 为空。
- `a_committed_restore_is_not_replayed_when_the_marker_cannot_be_removed`：用只允许读、拒绝删除的
  文件句柄模拟 pending 删不掉；恢复成功、标记仍在、`pending_restore=None`、第二次 `apply` 返回
  `Ok(None)`。
- `a_failed_completion_restores_uncheckpointed_journals_too`：失败回滚后 `-wal/-shm` 字节原样回到原位。
- `a_new_plan_is_not_suppressed_by_an_old_completion`：同一快照重新计划会得到新 `planId`，
  不会被上一次完成记录误吞。
- `a_runtime_takes_only_one_restore_attempt`：同一运行时第二次返回 false。
- 既有 `a_planned_restore_replaces_the_database_on_the_next_start_only`、schema 降级/清单隐瞒/
  篡改拒绝用例继续通过。
